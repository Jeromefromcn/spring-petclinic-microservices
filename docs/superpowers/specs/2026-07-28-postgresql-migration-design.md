# PostgreSQL Migration Design

Sub-project 2 of 4 from `CHANGES.md` (H2/HSQLDB default + MySQL optional profile →
PostgreSQL). Consul migration (sub-project 1) is done; chaos toggles and the
aggregation endpoint follow later.

## Context

Per `lab-environment/CLAUDE.md`'s cross-repo contract (the single source of truth
for values shared across the three repos):
- `lab-environment/docker-compose.yml` already runs a `postgres:16` container with
  three databases (`customers`, `vets`, `visits`), one per service, created via
  `POSTGRES_MULTIPLE_DATABASES` + `observability/postgres/init-multiple-databases.sh`.
- `lab-environment/scripts/init-consul-kv.sh` already seeds
  `config/<service>/data/{db.host,db.port,db.name,db.user,db.password}` into Consul
  KV for exactly `customers-service`, `vets-service`, `visits-service` — this fork
  does not read those keys yet.
- Only `customers-service`, `vets-service`, `visits-service`, `api-gateway` are
  actually built/deployed by `lab-environment`. `admin-server` and `genai-service`
  exist in the Maven reactor (needed project-wide once Config Server was deleted)
  but are never built into `ops-lab/*` images — no further work targets them,
  including this migration, even though `genai-service` happens to carry unused
  `hsqldb`/`mysql-connector-j`/JPA dependencies in its `pom.xml`.

Today, all three target services use HSQLDB (embedded, via
`db/hsqldb/schema.sql`+`data.sql`, `spring.sql.init` running on every start since
HSQLDB is an embedded database) as the default, with a `mysql` Spring profile
(`db/mysql/schema.sql`+`data.sql`) as a documented alternative for local MySQL. No
`postgresql` JDBC dependency, `postgres` profile, or `db/postgresql/` files exist
anywhere in the repo yet.

## Design

### Scope
Exactly `customers-service`, `vets-service`, `visits-service`. `admin-server` and
`genai-service` have no database role in `lab-environment` and are untouched.

### Dependency changes (`pom.xml`, all 3 services)
- Remove `com.mysql:mysql-connector-j` and the `mysql` profile's reason for
  existing along with it.
- Add `org.postgresql:postgresql` (runtime scope, matching how the removed MySQL
  driver was scoped).
- `org.hsqldb:hsqldb` stays, but scoped to `test` only — it's still what
  `application-test.yml` runs against; only the main/production classpath drops it.

### `application.yml` changes (all 3 services)

Default (root) document — add, alongside the existing
`spring.cloud.consul.host`/`port` keys from the Consul migration:
```yaml
spring:
  datasource:
    url: jdbc:postgresql://${db.host}:${db.port}/${db.name}
    username: ${db.user}
    password: ${db.password}
  sql:
    init:
      schema-locations: classpath*:db/postgresql/schema.sql
      data-locations: classpath*:db/postgresql/data.sql
      mode: always
```
`${db.host}`/`${db.port}`/`${db.name}`/`${db.user}`/`${db.password}` resolve from
the `config/<service>/data/db.*` Consul KV keys `lab-environment` already seeds —
no new KV convention needed, this fork just starts consuming what already exists.

`mode: always` (not the `never` that's typical for an external database) is
intentional: it preserves today's behavior where every service start gets a
freshly reset, deterministically seeded database, matching
`lab-environment/ROADMAP.md`'s "run scenario → wipe → next scenario" testing model.
The tradeoff — data added at runtime doesn't survive a restart — already holds true
today under HSQLDB and isn't a regression.

Remove: the `mysql` profile document entirely (was gated on
`on-profile: mysql`, set `spring.datasource.url: jdbc:mysql://...` and
`db/mysql` schema/data locations).

Docker-profile document, chaos-monkey profile document, and every other existing
key (Consul host/port, `vets-service`'s `cache`/`profiles` keys, etc.) — untouched.

### New `db/postgresql/schema.sql` + `data.sql` (all 3 services)

Structural base is each service's existing `db/hsqldb/schema.sql` (drop-and-recreate
style: `DROP TABLE IF EXISTS ...` then `CREATE TABLE`), because that matches the
`mode: always` deterministic-reset design above — not `db/mysql/schema.sql`'s
`CREATE TABLE IF NOT EXISTS` style, which would silently stop reseeding after the
first run.

Two real (non-cosmetic) schema facts from `db/mysql/schema.sql` are carried over
since they reflect upstream's actual intended schema, not artifacts of MySQL syntax:
- `customers-service`: `owners.telephone` is `VARCHAR(20)`, not hsqldb's `VARCHAR(12)`.
- `vets-service`: `vet_specialties` gets a `UNIQUE (vet_id, specialty_id)` constraint,
  which hsqldb's version lacks.

Postgres-specific translation, applied uniformly:
- `INTEGER IDENTITY PRIMARY KEY` → `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- Inline `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY` stays as separate
  statements after the `CREATE TABLE`s (Postgres supports this identically to
  HSQLDB; keeping it avoids an unnecessary diff from the source file).

Seed data (`data.sql`) keeps `db/hsqldb/data.sql`'s actual values (owners, pets,
vets, specialties, visits) — the only difference from `db/mysql/data.sql` here is
cosmetically different dates, not a correctness question.

**Sequence-restart fix (the one real correctness risk in this migration):** because
seed data hardcodes primary keys (`INSERT INTO owners VALUES (1, ...)` etc.),
Postgres's identity sequence for each table stays at its start value (1) — it does
not auto-advance to account for explicitly-inserted keys the way one might assume.
Without a fix, the first row a user creates through the running app (add
owner/pet/vet/visit) collides with an already-seeded id. `data.sql` ends with an
explicit per-table sequence restart, e.g. for `customers-service`:
```sql
ALTER SEQUENCE types_id_seq RESTART WITH 7;
ALTER SEQUENCE owners_id_seq RESTART WITH 11;
ALTER SEQUENCE pets_id_seq RESTART WITH 14;
```
(sequence names follow Postgres's default `GENERATED AS IDENTITY` naming:
`<table>_<column>_seq`; restart values are `max(seeded id) + 1` per table, derived
directly from each service's own seed data.) The same pattern applies to
`vets-service` (6 seeded `vets` rows, 3 seeded `specialties` rows — `vet_specialties`
has no identity column, so it needs no restart statement):
```sql
ALTER SEQUENCE vets_id_seq RESTART WITH 7;
ALTER SEQUENCE specialties_id_seq RESTART WITH 4;
```
and to `visits-service` (4 seeded `visits` rows):
```sql
ALTER SEQUENCE visits_id_seq RESTART WITH 5;
```

## Testing
- `./mvnw clean package -pl spring-petclinic-customers-service,spring-petclinic-vets-service,spring-petclinic-visits-service` — existing tests still pass unchanged (they run against HSQLDB via `application-test.yml`, untouched by this migration).
- Bring up `consul` + `postgres` + the 3 services via `lab-environment`'s compose (after running `init-consul-kv.sh`) and verify:
  1. Each service starts cleanly and connects to its own Postgres database (not just "port open" — query actual seeded rows through each service's REST API).
  2. Creating a new record through the running app (e.g. add an owner) does not collide with a seeded id — validates the sequence-restart fix.
  3. Restarting a service resets its data to the seeded state — validates `mode: always` behavior is preserved, not accidentally dropped to `never`.
